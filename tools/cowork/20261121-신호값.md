# 코워크 실행 지시 — 서울 신호값을 더 빨리·더 넓게 받는 길 (2026-11-21 · Claude Code 작성 · 소유자 「신호값을 어떻게 받는 게 좋을까 · 코워크에서 진행하게 · 클로드 코드와 연결까지 종합적으로」)

너는 형님(소유자) PC 에서 일한다. 저장소 `datamap`(지식베이스\datamap) 의 **CLAUDE.md 절대 규칙**을 먼저 읽고 따른다.

## 왜 이 일을 하나(Claude Code 가 2026-11-21 실측한 지금 상태)
- 서울 신호 교차로 2,765곳 중 **2,485곳은 실측 기록이 있다**. 그런데 요일 갈래(월~목·금·토·일) × 24시 = 96칸 가운데 **채운 칸은 46%**(한강 이남 여섯 구 64%) — 그리고 **하루에 0.1%p 도 안 는다**.
- 막힌 까닭은 둘이다.
  1. **하루 한도** — T-Data 열쇠 두 개(`t_data_seoul` · `t_data_seoul2`) 모두 **열쇠마다 하루 약 1,000번**을 이미 다 쓴다(11-20 실측: Fusion 521 · 상태 198 · 잔여+상태 역사 119 · 잔여 역사 157 = 995). Fusion(지금 한 줄) 한 번 = 교차로 하나 · 칸 하나라서 빈 칸 약 14만을 메우려면 몇 달이 걸린다.
  2. **역사 API 6시간 묶음** — `v2xSignalPhaseTimingInformation` 등 역사 API 는 01·07·13·19시 시작 6시간 묶음의 **앞 두 시간만** 끝까지 나오고 뒤 네 시간은 HTTP 500 으로 끊긴다(10-15·10-21 실측 · 요청 인자에 시각 고르기 없음 — 2026-10-15 코워크 결과 과제 2). 그래서 하루 24시 가운데 **16시간은 Fusion 한 줄로만** 메운다.
- 지금 수집 방식(앞 두 시간 역사 훑기 + 남은 칸만 골라 Fusion)은 이미 빈 칸부터 고른다. **같은 한도 안에서 더 짜낼 것은 거의 없다** → 판을 바꿀 길은 「한도를 늘리기」「한꺼번에 받는 길 찾기」「계획값 원본을 받기」 셋이다.

- 열쇠는 `07_API키\keys.json` 에만 있다. **읽지도 옮기지도 화면에 띄우지도 않는다.** 새 열쇠를 받으면 형님이 직접 `keys.json` 에 `"t_data_seoul3"` 처럼 **이름만 정해** 넣고, 결과 파일에는 「t_data_seoul3 넣음」처럼 **이름만** 적는다.

## 과제 1 — T-Data 하루 한도를 늘리는 길 (먼저)
t-data.seoul.go.kr 의 이용 안내 · 이용약관 · FAQ · 공지 · 마이페이지 안내에서:
1. **하루 호출 한도**(1,000번?)의 원문과 단위 — 열쇠마다인지 · API 마다인지 · 계정마다인지.
2. **한도를 늘리는 신청**(운영 계정 · 대용량 · 트래픽 증설 · 공공기관·연구 목적 등)이 있는지 · 있으면 신청 화면 주소 · 필요한 서류 · 걸리는 날.
3. **한 계정에서 열쇠를 더 받을 수 있는지**(활용 신청을 목적별로 따로 내면 열쇠가 따로 나오는지).
4. 신청이 있으면 **신청 글 초안**을 결과 파일에 쓴다 — 목적: 「경찰 교통 외근 업무 보조 연구개발(교차로 신호 운영 계획을 시간대별로 파악해 긴급 출동·정체 관리에 씀) · 비영리 · 받은 원자료는 공개하지 않고 묶은 값만 씀」 · 필요 호출 수: 「열쇠마다 하루 1만 번(서울 2,700여 교차로 × 하루 몇 번)」. 제출은 🙋 형님 몫.

## 과제 2 — 신호 이력을 한꺼번에 받는 길
1. T-Data **데이터셋(파일 내려받기)** 목록에서 「신호」「V2X」「SPaT」「잔여시간」「신호현시」로 찾아 **지난 날짜 신호 이력을 파일(CSV·zip)로 주는 것**이 있는지 · 있으면 데이터 이름 · data_id · 기간 · 파일 크기 · 받는 법(로그인 필요 여부).
2. 서울 열린데이터광장(data.seoul.go.kr) · 공공데이터포털(data.go.kr) · 국가교통DB(ktdb.go.kr) · 교통 빅데이터 플랫폼(bigdata-transportation.kr) · ITS 국가교통정보센터(its.go.kr)에서 **서울 교차로 신호 운영 계획(주기·현시·옵셋·시간대 계획)** 또는 신호 이력 파일을 같은 낱말로 찾는다. 경찰청 「교차로계획정보서비스」(서울 398곳 · 이미 씀)는 빼고 **새로운 것만** 적는다.
3. 찾은 것마다: 범위(서울 몇 곳) · 갱신 주기 · 이용 조건(공공누리 몇 유형 · 상업 금지·변경 금지 여부) · 주소.

## 과제 3 — 계획값 원본을 받는 길(가장 큰 한 방 · 조사와 초안만)
교통과에서 받은 현시도 5곳(KSC-5800SE 출력)이 실측과 87% 맞았다 — **계획값 원본이 실측보다 정확하다**(규칙 RULE-SIG-7). 서울 전체 신호제어기 계획값을 한 번에 받으면 몇 달 걸릴 일이 하루에 끝난다.
1. 정보공개포털(open.go.kr)에서 「신호 주기」「신호운영」「현시」「신호시간」으로 **이미 공개된 청구 사례**(서울특별시 · 서울경찰청 · 다른 시도)를 찾아 — 누가 무엇을 청구했고 공개·부분공개·비공개 중 무엇이었는지 · 비공개면 까닭(조항) · 주소.
2. 서울 신호 운영을 **어느 기관 어느 부서**가 맡는지(서울특별시 교통운영과·교통정보과 · 서울경찰청 교통안전과 등)를 기관 누리집 조직도에서 원문으로 확인 · 주소.
3. 위를 바탕으로 두 가지 **초안**을 결과 파일에 쓴다(보내지 않는다 · 🙋 형님 몫):
   - (가) 정보공개청구서 초안 — 청구 내용: 「서울시 관내 신호제어기별 시간대(TOD) 계획 · 패턴별 주기·현시 시간 · 특수일 계획 (교차로 번호·이름 포함 · 전자 파일)」 · 공개 방법: 전자 파일.
   - (나) 경찰 내부 협조 요청 초안 — 형님이 소속 경찰서 교통과를 통해 서울경찰청 신호 담당에 「신호제어기 데이터베이스 계획값 내보내기」를 부탁하는 짧은 글(목적 · 쓰는 곳 · 공개하지 않는다는 약속 · 받을 꼴(엑셀·CSV)). 이미 받은 5곳 현시도와 같은 표면 된다고 적는다.
